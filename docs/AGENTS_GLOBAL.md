## 语言偏好（强制）

- **所有回复默认用中文**（简体），包括：对话、解释、评审、报告、todo 文件内容、commit message 建议。
- 代码、命令、技术术语、库名、变量名、文件路径保持英文原样（不翻译）。
- 引用第三方文档原文时不翻译，保留原语言。
- 如果用户在某次对话里明确说「这次用英文」，则本次按英文，下一轮自动恢复中文。

## 工作流程（强制）

1. **收到任务时**：先建 todo 列表，列出所有要做的事（包括自我审查 + 测试），保存到 `docs/todos/YYYY-MM-DD.md`
2. **等用户确认**：todo 列表给用户看，**等用户说"执行"/"改"/"确认"后才开始**
3. **写代码前**：改动涉及 `.php` / `.py` / `.vue` / `.tsx` / SQL 时，**必须先加载对应规范技能**（`backend-spec` / `python-spec` / `etl-spec` / `frontend-spec`），即使你认为记得也要加载——不加载直接写代码视同违规。
4. **执行时**：逐个 todo 完成，每完成一个标记 `[x]`，更新 `docs/todos/` 文件
5. **影响面检查（强制）**：改动前必须查影响面，改动后必须报告影响面。
   - **触发条件**：改动涉及函数/方法签名、接口契约、表结构、路由、配置项、返回值结构时触发。
     单行 typo、常量值调整、注释修改不触发。
   - **查什么**：用 codegraph `callers`/`impact`（有索引时）或 grep（无索引时）找出所有调用方；
     涉及返回值结构变动的，查前端/消费端是否兼容新字段。
   - **不查的后果**：只改了调用点 A，漏改调用点 B → 线上回归。等同于"未测试就交付"。
6. **自我审查**：代码改完后，自我检查改动是否完整、是否遗漏边界情况
7. **测试**：按改动类型跑对应测试（PHP lint / Python AST / Vue build / DB 验证），结果写入 todo
8. **接口文档补全（开发接口时强制）**：新增或修改 API 接口后，必须同步补全接口文档。
   - **触发条件**：新增接口 / 修改接口入参或返回值结构时触发。
     纯内部重构（接口签名不变）不触发。
   - **文档标准**：按当前项目规范技能的接口文档格式（PHP 项目按 `php-code-style` 接口文档章节、前端项目按 `h5-code-style` API 对接约定）。
   - **文档位置**：项目内 `docs/api/`（具体文件名由项目 AGENTS.md 约定）。
   - **不补的后果**：接口上线但前端/消费端不知道字段含义 → 联调返工。
9. **完成后**：按完成报告模板输出验证报告，**每次改完提醒用户部署/推送**，不擅自推送
10. **经验回流**：每轮迭代结束，调用 `skill lessons-rollback` 把踩过的坑沉淀到项目 AGENTS.md

> **禁止**：建完 todo 后不经用户确认就开始执行代码改动。
> **任何文件修改前**（包括配置文件、文档、全局设置，不只是代码），必须先建 todo 并等用户确认。
>   擅自修改 AGENTS.md / 配置文件 / 文档视同违反工作流程。

### 原型驱动开发规则（强制）

> 适用场景：用户提供静态 HTML 原型（含模拟数据 + 全交互），AI 负责改造成 API 动态版。
> **原型由用户提供，AI 不写原型，只负责实现。改造 ≠ 重写——功能不变只换技术栈。**

#### 流程

1. **codegraph 定位 → Read 精读（数据块读前 50 条样本）**
   - **codegraph 先跑**（定位函数/调用链/文件结构，省 token）：
     - `codegraph_files` 看目录结构 → `codegraph_context` 拿入口点 → `codegraph_node` 看函数源码 → `codegraph_callers` 找调用方
   - **Read 精读逻辑段**（codegraph 定位后只读逻辑，数据块读前 50 条）：
     - **数据块读前 50 条样本**（不完全跳过）：内联数据 `const REVIEWS = [...]` / `var STORES = {...}` → **必读前 50 条**，理解 5 件事：
       1. 字段名 + 值类型（string/number/嵌套对象）
       2. 空值分布（哪些字段常为空：`city`/`dish`/`l1` 默认值是什么）
       3. 展示样式（"差 3/10" vs "30%" vs "3 条差评"——格式不能猜）
       4. 算法依据（排序键、颜色阈值、聚合字段、HAVING 条件）
       5. 数据量级（决定懒加载/分页/折叠策略）
     - 第 51+ 条跳过（省 token）；字段样本 + 算法依据同步落到 `.omo/evidence/` 功能清单
   - **codegraph 无索引 / 单体 HTML 时 fallback**：
     - `wc -l` + `grep -n "function\|addEventListener\|URLSearchParams"` 定位逻辑段行号 → 分段 Read

2. **落盘功能清单**到 `.omo/evidence/`（页面元素 + 交互行为 + URL 参数 + 数据字段）

3. **设计 API 字段，确保覆盖功能清单所有项**
   - 对照清单逐项检查：每个功能需要的 API 字段是否都有
   - 标出差异（漏了/改了/多了），补齐后才动代码

4. **按功能纵向切片执行**（衔接「任务拆分规则」）
   - 判别任务类型 → 开发功能 → 按功能纵向切片
   - 每个切片 = 后端 API + 前端页面 + 联调，做完验证再做下一个
   - 每个切片完成后，对照功能清单检查该项是否 1:1 覆盖

#### 禁止

- ❌ 用 grep 扫关键词代替逐行阅读（漏掉弹窗/懒加载/tab 切换等交互行为）
- ❌ 未读完原型文件就动手写代码
- ❌ 只覆盖"数据展示"类功能，漏掉"交互行为"类功能
- ❌ 功能清单只存在对话里不落盘
- ❌ 擅自增减功能
- ❌ 读大文件时逐行读全部内联数据（浪费 token，数据块只读前 50 条样本，51+ 跳过）

### 任务拆分规则（强制）

**第一步：判别任务类型**

| 任务类型 | 判断标准 | 拆分策略 |
|---|---|---|
| **修 bug** | 恢复已有行为；范围 1-3 文件；验证「原来坏的现在好了」 | **不切片**。一个根因 = 一个原子 todo |
| **开发功能** | 创造新行为；范围 5+ 文件；验证「新功能端到端可用」 | **按功能纵向切片**（第二步） |
| **重构** | 改结构不改行为；验证「功能不变 + 代码更清晰」 | **按代码模块切片**（第三步） |

**关键**：bug 找根因不切片；功能必须端到端可演示；重构必须证明行为不变。

**第二步（开发功能）：纵向切片**

核心原则：**按功能切片，不按技术层切片**。一个切片 = 后端 API + 前端页面 + 联调测试，三者一组端到端可验证。**触发条件（任一）**：① 同时涉及前后端 ② 多个独立功能模块 ③ 工作量 ≥ 2 天。**执行**：每个切片做完验证才做下一个；每个切片独立 commit；后端先行（前端没数据没法测）；公共基建作为切片 0 先做。

**第三步（重构）：按代码模块切片**

3 条铁律：
1. **每个切片必须有「行为不变」证据**（数据条数、API 字段、跳转路径对比）——无证据等于引 bug
2. **按代码模块切，不按重构手法切**（同一文件被改 3 遍 = 3 倍风险）
3. **按依赖顺序改**：Model → Service → Controller → 前端，先底层后上层

**反模式（禁止）**：

| 反模式 | 为什么禁止 |
|---|---|
| 先做完所有后端，再做所有前端 | 后端没法验证（没前端）；前端做时发现后端设计错要返工 |
| 一个 todo 包含多个功能 / 切片粒度太粗 | 无法独立验证、无法独立回滚 |
| 切片粒度太细（一个 SQL 一个切片） | 碎片化，失去端到端可验证的意义 |
| 重构没跑「行为不变」验证就 commit | 重构引 bug 的头号原因 |
| 同一文件跨多个切片改 | 每次改动都有风险，改 N 次 = N 倍风险 |
| 重构时「顺手」加新功能 | 混淆「行为不变」和「加了新能力」，无法验证 |

**切片模板**：开发功能切片 / 重构切片的标准 markdown 模板见 `skills/init-project/SAMPLE-AGENTS-ACA.md`。

### todo 文件格式（`docs/todos/YYYY-MM-DD.md`）

```markdown
# YYYY-MM-DD 任务清单
> 状态：待确认 / 执行中 / 已完成
## 待办
- [ ] 1. 改动任务描述（文件:行号）
- [ ] 2. 影响面检查（codegraph callers/impact 或 grep 找调用方）
- [ ] 3. 自我审查（检查改动完整性）
- [ ] 4. 测试验证（php -l / python ast / npm build / DB）
- [ ] 5. 接口文档补全（开发接口时，按项目规范技能格式，位置 docs/api/）
## 已完成
- [x] X. 已完成任务描述
## 测试结果
- 命令：`xxx`
- 输出：实际结果
```

### 完成报告模板

**有就列出，没有不列出。不要硬凑。**

```markdown
## <commit hash 或任务名> 完成报告
### 改动文件
| 文件 | 改动行 |
|------|--------|
| `绝对路径/文件` | +N -M |
### 代码 diff
- Line N: 旧值 → 新值
### 影响面
| 改动符号 | 调用方 | 是否受影响 | 说明 |
|----------|--------|-----------|------|
| `funcA` | `callerB` (file:line) | ✅ 已处理 / ⚠️ 副作用 / ❌ 无影响 | 一句话说明 |
- 前端兼容性：✅/❌（字段 X 已支持/需改）
- 数据库兼容性：✅/❌
- 未触发影响面检查时写：`本改动为 [typos/常量/注释]，未触发影响面检查。`
### 测试
- 命令：`xxx`
- 输出：实际结果（exit code / stdout / DB state）
### 接口文档
- 位置：`docs/api/xxx.html`（新增 C05 接口区块 / 修改字段说明）
- 标准：按 php-code-style 接口文档格式（响应字段表 + 请求示例 + curl 示例 + notes 口径说明）
- 未触发接口文档补全时写：`本改动未改接口签名，未触发接口文档补全。`
### Git
- commit: `hash 简述`
- branch: `v2`
- push: 成功/失败
### 风险/后续
- （没有就跳过）
```

**规则**：绝对不写"改好了"/"完成了"（无证据）；必须给文件路径/行号/命令/输出；每次改完提醒用户部署/推送。

## git 操作安全

- **不擅自推送**：等用户确认
- **不擅自 commit**：等用户说"提交"/"推送"
- **reset --hard 前确认**：可能有未保存的工作
- **部署脚本已覆盖的不要重复**：用项目既有部署命令，不自己造轮子
